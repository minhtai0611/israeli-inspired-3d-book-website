# Accessibility — Phase 6 checklist

What was actually checked and fixed, with the real numbers behind each claim.
This is **not** a full accessibility audit — it's the specific set of issues
identified in the plan's Phase 6, verified before and after the fix.

## What was NOT done

No screen-reader session (NVDA/VoiceOver) was run against this build. The
checks below are: computed contrast ratios (WCAG formula, script-verified),
static analysis (`grep` across `src/`), and manual keyboard-only navigation
in a browser. A real screen-reader pass is worth doing before relying on
this document as a complete a11y sign-off.

## `lang` attributes on bilingual text

**Problem**: `<html lang="vi">`, but Hebrew text only had `dir="rtl"` — no
`lang="he"`. A screen reader has no signal that the text is Hebrew and reads
it using Vietnamese pronunciation rules.

Added `lang="he"` to every real Hebrew-text element (`heTitle`, `heRef`,
verse text, hero quotes, the 404 page, the about page's closing line) across
9 files, and `lang="en"` to the English verse text in the reader. A few
`dir="rtl"` elements remain without `lang="he"` on the *same line* (so they
still show up if you grep single-line): two of them (`sach/[book]/page.tsx`,
`thu-vien/page.tsx`) have `lang="he"` on the very next line in multi-line
JSX — genuinely fixed, just not visible to a same-line grep. The third
(`ReaderView.tsx`'s verse-number span, `{v.n}.`) is a bare Arabic numeral
styled to visually align like Hebrew text — it isn't actually Hebrew-language
content, so it wasn't tagged.

## Contrast

Computed with the standard WCAG relative-luminance formula (script, not
eyeballed) against this site's actual colors:

| Element | Before | After | Ratio before | Ratio after |
|---|---|---|---|---|
| `text-parchment/40` on `#0b1220` | 40% opacity | `/60` | 3.37:1 **FAIL** | 6.15:1 PASS |
| `text-parchment/50` on `#0b1220` | 50% opacity | `/60` | 4.61:1 (borderline pass) | 6.15:1 PASS |
| Copy-link icon, resting state, on parchment (`#f4ead2`) | `#a37d1a` @ 50% opacity | `#6b4f0a` @ 90% opacity | 1.70:1 **FAIL** | 5.09:1 PASS |

Note on the copy-link fix: the plan's own suggested replacement
(`opacity-60` for the resting/dimmed state) was checked and it **also
fails** — `#6b4f0a` at 60% opacity over the parchment background computes to
2.70:1, still below the 4.5:1 normal-text threshold this button's 11px text
needs (it isn't large enough to qualify for the 3:1 large-text exception).
Used 90% opacity instead (5.09:1), which keeps the "dim until hover/focus"
visual intent while actually passing.

All `text-parchment/40` and `/50` instances across the codebase were changed
to `/60` (verified: `grep -rn "text-parchment/40" src/` → 0 matches).

## Other fixes

- `HebrewMarquee` and `HeroOrbit` (purely decorative, no semantic content)
  now have `aria-hidden="true"` — previously a screen reader would read 44
  disconnected Hebrew letters or an unlabeled orbiting SVG scene.
- Copy-verse-link's empty `catch {}` now falls back to a `textarea` +
  `execCommand("copy")` if the async Clipboard API is unavailable
  (non-HTTPS/older browser), and reports failure via a visible message
  instead of silently doing nothing.
- Added an `aria-live="polite"` status region announcing "Đã sao chép liên
  kết câu N" (or the failure message) — previously copying a verse link gave
  no feedback to screen reader users at all.
- The reader's verse `<ol>` now has an `aria-label` identifying which
  book/chapter it lists.
- `/doc/[book]/[chapter]`'s "N câu · Song ngữ..." line changed from `<p>` to
  `<h2>` — it was the only sub-heading-shaped content on the page and had no
  heading tag at all, leaving `<h1>` with nothing beneath it in the heading
  outline.
- Added a `prefers-contrast: more` media query (alongside the existing
  `prefers-reduced-motion` block in `globals.css`) that forces
  `.glass` panels to a solid background and every dimmed
  `text-parchment/{60,65,70,75,80,85,90}` variant to full opacity.

## Manual keyboard check

Tabbed through the homepage, `/thu-vien`, a `/sach/[book]` page, and
`/doc/[book]/[chapter]`'s reader controls + verse list + prev/next nav.
Every interactive element (search input, sort toggle, pagination links,
font-size/line-spacing/language-mode buttons, copy-link buttons, prev/next
chapter cards) reached a visible focus state via `:focus-visible` — no
keyboard traps, no invisible-focus elements found. This was a visual check
in a browser (Tab/Shift+Tab), not an automated audit.
